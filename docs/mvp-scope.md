# MVP のスコープ

この文書は hayami の最初の MVP で実現する範囲、対象外 (non-goals)、完了を判定する acceptance criteria を定めます。Issue #35 に対応します。画面構造、ショートカットキーの詳細、GitHub 認証や API クライアントの設計、実装タスクへの分解はこの文書では扱いません。

## 前提

- UI フレームワークは GPUI + gpui-kit (gpui-component) を使います (#20、#25 の評価結果による)。
- 対象サービスは GitHub、対象プラットフォームは macOS と Linux です (README.md)。
- プロトタイプ (#25) では、ローカルの diff ファイルを入力として、ファイル一覧、unified diff の表示、行・範囲選択とインラインコメント、キーボード操作、日本語 IME での入力を確認済みです。コメントはアプリ内で保持するだけでした。

## MVP の目的

「自分の PR レビューを、ブラウザを開かずに hayami だけで最後まで終えられる」ことを MVP の目的とします。プロトタイプで確認したのは閲覧とコメント入力までなので、MVP ではそれを GitHub 上の実際の PR につなぎ、レビューを投稿するところまでを実現します。

## 最小のユーザーフロー

1. 端末から PR の URL を指定して hayami を起動する (例: `hayami https://github.com/owner/repo/pull/123`)。
2. PR のタイトルと変更ファイルの一覧、選択したファイルの unified diff が表示される。
3. キーボードでファイル間、change group 間を移動し、diff を読む。
4. 行または行範囲を選択してコメントを書く (日本語 IME を含む)。書いたコメントは送信前の下書きとしてアプリ内に保持され、diff 上にインライン表示される。下書きは編集・削除できる。
5. レビュー全体のコメント (本文) を書き、Comment / Approve / Request changes のいずれかを選んでレビューを送信する。下書きのインラインコメントは、このレビューの一部として 1 回でまとめて GitHub に投稿される。
6. 送信の成否が表示される。失敗した場合は下書きが失われず、再送信できる。

## 決定事項

Issue #35 で挙げられた論点ごとの決定です。

### 入力

- **GitHub PR URL を主な入力とします。** レビュー結果を GitHub に投稿するには PR が必要なためです。
- **ローカルの diff ファイルも入力として残します。** 開発・テストで fixture を使うため、またネットワークなしで動作を確認するためです。diff ファイルを入力にした場合は閲覧とコメントの下書きまでで、GitHub への投稿はできません。

### コメントの扱い

- **GitHub への投稿まで MVP に含めます。** アプリ内で保持するだけでは、実際のレビューに使えないためです。
- コメントは 1 件ずつ即時に投稿するのではなく、下書きとして溜めてレビュー送信時にまとめて投稿します (GitHub の pending review と同じモデル)。
- 既存のレビューコメントやスレッドの表示、返信、resolve は MVP に含めません (non-goals を参照)。

### レビュー完了

- **Comment / Approve / Request changes によるレビュー送信を MVP に含めます。** GitHub の API ではインラインコメントの投稿とレビューの完了が 1 回のレビュー送信にまとまっているため、投稿を含めるならレビュー完了を分ける理由が小さいためです。

### 必須にする UI 要素と操作

| 要素 | MVP | 備考 |
| --- | --- | --- |
| ファイル一覧 | 必須 | 選択したファイルへの移動と、現在表示しているファイルのハイライト |
| unified diff | 必須 | シンタックスハイライト、行番号、追加・削除行の区別 |
| split (side-by-side) diff | 対象外 | |
| 折りたたみ | 必須 (ファイル単位) | hunk 単位の折りたたみは gpui-component の公開 API にないため対象外 |
| 行選択・範囲選択 | 必須 | 範囲は同じファイル・同じ side 内の連続した行 |
| コメント入力 | 必須 | 日本語 IME での入力・確定・投稿を含む。下書きの編集・削除 |
| レビュー送信 | 必須 | 本文と Comment / Approve / Request changes の選択 |
| キーボード操作 | 必須 | 上記フローのすべての操作をマウスなしで行えること。具体的なキー割り当ては #34 で決める |
| マウス操作 | 必須 (最低限) | ファイルの選択、行の選択、コメント欄の操作、スクロール |

### パフォーマンスと大規模 diff

- 計測の基準は GPU を使える実機 (macOS の Apple Silicon、Linux の GPU のある環境) とします。GPU のない VM でのソフトウェア描画は参考値とします。
- 基準とする diff は、#25 の fixture (ripgrep PR #2610、32 ファイル・4,468 行) と、それ以上の規模 (100 ファイル以上・20,000 行程度) の diff の 2 つとします。
- 次の値を最低要件とします。
  - 4,468 行の diff を連続スクロールしたとき、平均フレーム時間が 16.7 ms (60 fps) 以下であること (#25 の macOS では約 34 ms で、MVP で改善が必要)。p95 は 33 ms 以下とする。
  - 20,000 行程度の diff でも操作不能にならず、スクロールと移動ができること (フレーム時間の目標値は設けない)。
  - PR の取得完了から最初の diff が表示されるまでが 1 秒以内であること (ネットワークの時間は含めない)。
- 1 ファイルが極端に大きい場合 (生成ファイルなど) やバイナリファイルは、内容を表示せずファイル名と「表示しない」旨のみを示してよいとします。

## Non-goals

MVP では次を扱いません。

- 既存のレビューコメント・スレッドの表示、返信、resolve
- PR の一覧、検索、通知 (受信箱) の表示
- split (side-by-side) diff、hunk 単位の折りたたみ
- 複数の PR を同時に開くこと (タブ・ウィンドウ)
- commit 単位の表示や、前回レビュー時からの差分の表示
- suggestion (提案変更) の作成
- ファイル全体の表示や、diff の範囲外の行へのコメント
- PR 本文、CI の状態、会話タブの表示
- PR の作成、マージ、ラベルやレビュアーの変更
- キーバインドのカスタマイズと設定 UI
- GitHub Enterprise Server への対応
- 署名、notarization、配布用パッケージの作成
- アクセシビリティ (VoiceOver / Orca) への対応

## Acceptance criteria

次をすべて満たしたとき、MVP を完了とします。

1. macOS と Linux の両方で、PR の URL を指定して hayami を起動すると、その PR の変更ファイル一覧と diff が表示される。
2. ローカルの diff ファイルを指定して起動すると、同じように表示される (投稿は無効)。
3. マウスを使わずに、ファイル間・change group 間の移動、ファイルの折りたたみ、行・範囲の選択、コメントの開始・入力・キャンセル、レビューの送信ができる。
4. 日本語 IME (macOS のことえり、Linux の fcitx5-mozc) でコメントを入力でき、変換中の Enter でコメントやレビューが誤って送信されない。
5. 単一行と複数行のコメントを下書きとして追加・編集・削除でき、diff 上の正しい位置に表示される。
6. Comment / Approve / Request changes のそれぞれでレビューを送信すると、GitHub 上で同じ種類のレビューとして、下書きのインラインコメントが正しいファイル・行・side に投稿される。
7. 送信に失敗したとき (ネットワークエラー、権限不足など) にエラーが表示され、下書きが失われずに再送信できる。
8. 「パフォーマンスと大規模 diff」の最低要件を満たす。
9. diff のパース、レビューモデル (下書きの追加・削除・アンカー)、GitHub API に送るリクエストの組み立てに自動テストがあり、CI で実行される。

## 後続の Issue

次の 3 つを後続の Issue として切り出します。いずれもこの文書のスコープを前提とし、#34 (ショートカットキーの仕様) と並行して進められます。

- **画面構造と状態遷移**: 起動から送信までの画面構成 (ファイル一覧、diff、コメント欄、レビュー送信のダイアログ)、フォーカスの移動、読み込み中・エラー時の状態。#34 のフォーカスと IME の扱いと関係が深いため、#34 と相互に参照します。
- **レビューモデルとモジュール境界**: diff のモデル、コメントのアンカー (ファイル・side・行範囲)、下書きとレビュー送信のモデル、UI と GitHub 連携を分けるモジュール境界。GitHub 認証と API クライアントの設計もここで扱うか、別の Issue にするかを決めます。
- **起動・入力インターフェース**: コマンドラインの引数 (PR URL、diff ファイル)、URL 以外の指定方法 (`owner/repo#123` など) の要否、GitHub の認証情報の取得方法 (`gh` CLI の認証の利用、環境変数のトークンなど)。
